Era / Emuera 数据层

CSV 不是杂项配置，而是 era 游戏的数据骨架

这篇专栏基于原版 Emuera 源码和 eratohoK 示例工程，解释每类 CSV 的作用、加载时机、写法、迁移方法，以及在 Pyera 项目里怎样把 CSV 与 Python 代码配合起来。

参考数据 eratohok-master/CSV 包含大型实战 CSV 组织方式
面向项目 Pyera / era Python 脚本层与 Emuera 变量系统互操作

1. CSV 的心智模型

在传统 ERB 项目里，CSV 经常被误解成“放名字的地方”。实际更准确的理解是：CSV 为 Emuera 的固定变量系统提供 名字表、数组尺寸、初始角色模板和少量系统元信息。ERB 或 Pyera 代码运行时使用的是变量，例如 CFLAG、ABL、FLAG、ITEM；CSV 决定这些变量的索引是什么意思。

名字表

把数字索引翻译成人能读懂的名字

ABL.csv 的 10,侵攻 让 ABL:10 有了含义。代码仍然访问索引，CSV 负责命名。

尺寸表

决定变量数组可以开多大

VariableSize.csv 可以把 CFLAG 扩到 20000。大项目必须先规划尺寸，避免后期越界或存档迁移困难。

模板表

定义角色创建时的初始状态

Chara*.csv 不是角色存档，而是角色模板。ADDCHARA 或初始角色加载会基于模板生成运行时角色。

给 Pyera 项目的结论： Python 代码适合写流程、系统、算法和第三方库集成；CSV 适合保存稳定的编号体系和初始数据。不要把所有游戏设定硬编码进 Python，也不要把复杂逻辑塞回 CSV。

2. Emuera 的加载顺序

根据 Process.Initialize 和 ConstantData.LoadData，启动阶段大致按下面顺序处理 CSV。理解这个顺序很重要，因为后面的 CSV 会依赖前面建立好的尺寸和名字表。

01 _Replace.csv

如果配置启用，先覆盖部分 emuera.config 项，例如界面文字、分隔线、系统标签。

02 _Rename.csv

如果配置启用，建立 [[别名]] -> 实际标识符 的替换字典，主要影响脚本读取。

03 GAMEBASE.CSV

读取游戏代码、版本、标题、作者、最初角色、兼容版本等元信息。

04 VariableSize.CSV

先调整变量数组大小，再为后续名字表和角色变量分配空间。

05 固定名字表

读取 ABL、BASE、CFLAG、ITEM、STR 等 CSV。

06 Chara*.csv

扫描角色模板文件。是否递归扫描子目录受 Emuera 的 SearchSubdirectory 配置影响。

3. 固定 CSV 文件总览

下面按职责分类说明常见 CSV。Emuera 文件名匹配通常不区分大小写，但项目里建议统一使用明确大小写，避免跨平台工具链和版本管理混乱。

3.1 项目元信息与装载控制

GameBase.csv
游戏身份与版本信息。

常见键包括 コード、バージョン、タイトル、作者、製作年、追加情報、ウィンドウタイトル、最初からいるキャラ。存档兼容、窗口标题和默认角色都来自这里。

VariableSize.csv
变量数组尺寸表。

格式通常是 变量名,长度。例如 eratohoK 将 CFLAG 和 CFLAGNAME 扩到 20000。对应变量和对应名字表不一定自动同步，除 ITEMNAME 与 ITEMPRICE 有特殊联动外，建议成对写清。

_Replace.csv
覆盖配置项。

在配置启用 UseReplaceFile 时读取。适合改显示标签、分隔线、加载文字等配置，不适合放游戏规则。

_Rename.csv
脚本别名替换。

源码中右侧是脚本里的 [[显示名]]，左侧是替换成的实际标识符。它可以改善 ERB 可读性，但在 Pyera 项目里更推荐用 Python 常量、枚举或 dataclass 建立可读名称。

3.2 角色能力与训练参数

Base.csv基础参数名

定义 BASE / MAXBASE 的索引含义，例如体力、气力、精神力。

Abl.csv能力名

定义 ABL 索引，例如性知識、侵攻、武勇、速度。角色模板中的 能力,名称,值 会映射到这里。

Talent.csv素质名

定义 TALENT 索引。适合放稳定的角色特质、体质、出身、标签和开关型属性。

Exp.csv经验名

定义 EXP 索引。用于长期积累的经验、熟练度、经历计数。

Mark.csv刻印名

定义 MARK 索引。传统 era 项目常用来表达阶段性、不可逆或半永久状态。

Palam.csv调教参数名

定义 PALAM、JUEL、UP、DOWN 等相关索引。

Source.csv参数来源名

定义 SOURCE，表示当前命令产生的参数来源，用于结算。

Ex.csv绝顶/事件计数名

定义 EX、NOWEX 一类短期或阶段内计数。

Train.csv命令名

定义 TRAINNAME，通常与选择命令、训练命令、菜单显示相关。

3.3 物品、装备与临时状态

Item.csv物品名与价格

通常格式是 编号,名称,价格。读取后对应 ITEMNAME、ITEMPRICE 和运行时 ITEM。

Equip.csv装备名

定义 EQUIPNAME。部分项目少用或不用，但保留给角色装备类状态。

Tequip.csv训练中装备名

定义 TEQUIPNAME，对应 TEQUIP。传统项目常用于命令执行期间的临时装备或状态。

Stain.csv污渍/附着状态名

定义 STAINNAME，对应角色变量 STAIN。

3.4 全局与角色自定义变量名

Flag.csv全局数值标志名

定义 FLAGNAME，对应保存型全局数值数组 FLAG。适合剧情进度、系统开关、全局状态。

Tflag.csv临时全局标志名

定义 TFLAGNAME，对应 TFLAG。适合一轮事件、一段流程内的临时状态。

CFLAG.csv角色数值标志名

定义 CFLAGNAME，对应每个角色自己的 CFLAG。这是角色长期状态最常用的扩展区。

Tcvar.csv角色临时数值名

定义 TCVARNAME，对应角色变量 TCVAR。适合临时计算，不建议作为长期存档字段。

CSTR.csv角色字符串名

定义 CSTRNAME，对应角色字符串数组 CSTR。适合称呼、文本标签、动态描述。

Str.csv全局字符串名

定义 STRNAME，对应可写的 STR。适合运行中字符串缓存。

Tstr.csv临时字符串名

定义 TSTRNAME，对应 TSTR。适合短生命周期字符串。

Savestr.csv保存字符串名

定义 SAVESTRNAME，对应会进入存档的 SAVESTR。

Global.csv跨存档数值名

定义 GLOBALNAME，对应全局数值变量 GLOBAL。适合成就、周回、全局设置。

Globals.csv跨存档字符串名

定义 GLOBALSNAME，对应全局字符串变量 GLOBALS。

Day.csv日期数组名

EE 扩展读取，定义 DAYNAME，对应 DAY。

Time.csv时间数组名

EE 扩展读取，定义 TIMENAME，对应 TIME。

Money.csv货币数组名

EE 扩展读取，定义 MONEYNAME，对应 MONEY。适合多货币或资源。

CDFLAG1.csv / CDFLAG2.csv二维角色标志轴名

定义 CDFLAGNAME1 与 CDFLAGNAME2，用于二维角色变量 CDFLAG。适合“角色 x 对象”“角色 x 部位”等矩阵型数据。

3.5 示例项目里出现但不是固定加载入口的文件

eratohoK 的 CSV 目录还包含 Juel.csv、train.txt、_default.config、_fixed.config、Chara.rar 等。这些文件对该项目有意义，但不属于 ConstantData.LoadData 固定读取的标准名字表。迁移时要先搜索脚本里是否引用它们，再决定保留、改名或删除。

4. Chara*.csv 角色模板

角色模板文件通常命名为 Chara0 xxx.csv、Chara1 xxx.csv。Emuera 通过 Config.GetFiles(csvDir, "CHARA*.CSV") 扫描，是否读取子目录取决于 SearchSubdirectory。eratohoK 把角色放在 CSV/Chara/，这是一种适合大型项目的组织方式。

角色模板编号。

对应角色的 NO，也是添加角色、查找角色、关系数组常用的稳定 ID。

名前
正式名称。

对应 NAME，用于系统显示、角色识别和默认文本。

呼び名
称呼名。

对应 CALLNAME，常用于对话和菜单。

基礎
基础参数初值。

第二列通常写 Base.csv 里的名字，第三列写数值，映射到 BASE 和 MAXBASE。

能力
能力初值。

第二列对应 Abl.csv，第三列为 ABL 初值。

素質
素质或标签。

第二列对应 Talent.csv。第三列为空时通常表示布尔型素质存在，写数值时表示带等级或参数的素质。

CFLAG
角色自定义数值。

第二列可写编号或 CFLAG.csv 名称，第三列为初始值。适合项目自定义长期状态。

CSTR
角色自定义字符串。

第二列可写编号或 CSTR.csv 名称，第三列为字符串初值。

相性
关系初值。

常用于初始化角色对其他角色编号的关系值。大型项目要谨慎维护编号稳定性。

5. 在 Pyera 里怎么用 CSV

Pyera 不应该复刻 ERB 的所有写法。更推荐做法是：CSV 继续承担稳定编号和初始数据，Python 侧建立轻量常量或缓存视图，把高频逻辑留在 Python 内部批量处理，最后再写回 Emuera 变量。

建议的 Python 访问风格
import era

# 常量可以由 CSV 生成，也可以手写在 py/game/ids.py
CFLAG_AFFECTION = 2
ABL_SPEED = 30

def show_profile(chara_index: int) -> None:
    c = era.chara(chara_index)
    name = c.name
    affection = c.cflag[CFLAG_AFFECTION]
    speed = c.abl[ABL_SPEED]
    era.print_line(f"{name} 好感度 {affection} / 速度 {speed}")

def add_affection(chara_index: int, value: int) -> None:
    c = era.chara(chara_index)
    c.cflag[CFLAG_AFFECTION] = c.cflag[CFLAG_AFFECTION] + value
性能原则： 不要像传统 ERB 那样一行一行跨桥查询。Python 侧可以缓存 CSV 名字表、角色视图和配置；批量计算后再一次性提交给 Emuera。复杂项目的优势来自模块化、缓存、批处理和第三方库，不来自单次变量访问更快。

6. 最佳实践

01 编号一旦发布就不要随意重排

CSV 索引会进入存档、角色模板和脚本逻辑。删除旧字段时优先标注废弃，保留编号空洞，而不是把后面的编号整体前移。

02 给每个范围留注释和分段

例如 CFLAG 1-99 放身份与关系，100-199 放剧情进度，1000+ 放系统扩展。大型项目没有分段会很快失控。

03 长期状态用保存变量，临时状态用临时变量

FLAG、CFLAG、SAVESTR 适合存档；TFLAG、TCVAR、TSTR 适合流程内临时值。

04 角色独有状态优先放 CFLAG / CSTR

不要把每个角色的长期差异塞进全局 FLAG。角色状态跟着角色走，Python 侧也更容易封装成 Chara 视图。

05 不要盲目复制旧项目 CSV

复制 eratohoK 这种大型项目的 CSV 会带来大量不适合当前主题的字段。更好的方式是先建最小集合，再按系统需要扩展。

06 为 Pyera 生成常量层

可以从 CSV 生成 ids.py，让 Python 代码写 CFLAG.AFFECTION 而不是到处写裸数字。

7. 从现有 era CSV 迁移到新主题

如果你从其他 era 游戏复制了一整套 CSV，第一步不是翻译文本，而是判断每个字段是否服务于你的新主题。对 Pyera 项目来说，建议按下面顺序迁移。

  1. 保留最小引擎必需层：GameBase.csv、VariableSize.csv、Base.csv、Abl.csv、Talent.csv、CFLAG.csv、CSTR.csv、Flag.csv。
  2. 删除不服务主题的旧字段：先不要保留几千个看不懂的旧编号。保留会制造错误安全感，后面写代码时更难判断字段含义。
  3. 为主题建立新的编号规划：例如角色生态、寄生状态、虫巢关系、身体部位、资源、事件进度分别使用独立编号段。
  4. 把复杂规则放到 Python：CSV 记录“有哪些字段”和“初始值”，Python 负责计算变化、触发事件、批量同步。
  5. 写迁移脚本而不是手工改存档：如果项目已经有玩家存档，新增字段可以默认 0；删除字段则保留废弃编号，避免破坏旧档。
